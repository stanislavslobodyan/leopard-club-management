# Інтеграція з комп’ютерами клубу: межі та наступний етап

## Поточний стан

У LEOPARD немає PC-agent процесу, мережевого протоколу чи збору heartbeat. Статуси «Активний», «Заброньований» і «Вільний» описують облікові сеанси й бронювання в базі. Вони не підтверджують, що фізичний ПК увімкнений або доступний у мережі.

Щоб реалізувати раніше обрану функцію справжнього моніторингу, потрібен окремо встановлений агент на кожному клубному ПК. Без нього інтерфейс не повинен показувати вигаданий online/offline.

## Запропонований протокол для узгодження

Можливий початковий контракт — HTTP API всередині LAN із TLS, унікальним секретом для кожного вузла, ротацією секретів і журналом адміністративних команд.

| Метод | Шлях | Призначення |
|---|---|---|
| GET | `/api/v1/health` | Heartbeat, версія агента, час останнього запуску, стан служби |
| GET | `/api/v1/hardware` | Фактичні CPU, GPU, RAM, накопичувач і монітор, якщо агент може їх зібрати |
| POST | `/api/v1/commands/lock` | Заблокувати робочу сесію з ідентифікатором команди |
| POST | `/api/v1/commands/unlock` | Розблокувати її після явного дозволу адміністратора |
| GET | `/api/v1/commands/{id}` | Підтвердити виконання чи повернути помилку команди |

Приклад heartbeat-відповіді (це схема майбутнього протоколу, не поточні дані LEOPARD):

```json
{
  "agentId": "site-01-pc-01",
  "agentVersion": "1.0.0",
  "observedAt": "2026-11-05T12:30:00Z",
  "health": "ready"
}
```

## Перед реалізацією

Потрібно узгодити LAN/VPN і сертифікати, спосіб розгортання Windows-служби, дозволені команди, автентифікацію, правила відмови/таймаутів та інвентар реальних ПК. Для керування екраном і запуском ігор треба окремо визначити вимоги безпеки та згоду клубу. Після цього можна додати client-service у desktop-проєкт і companion-agent для Windows PCs, а потім перевірити їх на фізичних машинах.
