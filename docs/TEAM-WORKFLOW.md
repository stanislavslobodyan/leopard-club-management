# Командний таск-менеджмент LEOPARD

## Для чого це

Команда веде роботу над LEOPARD через GitHub Issues. Кожна задача, помилка або пропозиція має власний Issue, де залишаються вимоги, обговорення, виконавець і посилання на код. README та документація описують продукт і процес, але не замінюють список поточних задач.

Шаблони створення Issue лежать у `.github/ISSUE_TEMPLATE`. Для великих змін використовуй [шаблон технічного завдання](TECHNICAL-TASK-TEMPLATE.md). GitHub Projects можна додати як дошку для перегляду тих самих Issues.

## Як почати задачу

1. У репозиторії відкрий **Issues → New issue** і вибери **Помилка**, **Нова можливість** або **Технічна задача**.
2. Опиши одну зрозумілу зміну. Якщо результат можна прийняти або відхилити окремо, заведи окремий Issue.
3. Вкажи пріоритет і заповни критерії приймання. Для змін у коді додай спосіб перевірки.
4. Під час тріажу признач відповідального. Якщо команда використовує GitHub Projects, додай Issue до проєкту й задай його статус.
5. Працюй у гілці на кшталт `feature/42-search-clients`, `fix/37-session-total` або `docs/18-team-workflow`.
6. У Pull Request додай `Closes #номер`, заповни шаблон PR і переведи картку в **In review**.
7. Після перевірки й злиття закрий Issue та познач його **Done** у Project.

## Статуси для дошки GitHub Projects

Якщо для команди створена Project board, використовуй поле **Status** з такими значеннями:

| Статус | Коли ставити |
|---|---|
| Backlog | Запит зафіксований, але ще не готовий до роботи |
| Ready | Є відповідальний, обсяг і критерії приймання |
| In progress | Робота над зміною вже триває |
| Blocked | Роботу зупинила залежність або відсутнє рішення |
| In review | Відкрито Pull Request і потрібна перевірка |
| Done | Зміну прийнято та змерджено або запит закрито з поясненням |

Рекомендоване поле **Priority**: **P0 — терміново**, **P1 — висока**, **P2 — звичайна**, **P3 — низька**. Пріоритет задається під час тріажу; дедлайн вказується лише тоді, коли він справді відомий. Виконавець зберігається як assignee Issue. Команда може додати поле **Size** (XS/S/M/L), якщо оцінки допомагають плануванню.

Щоб створити дошку: у репозиторії відкрий **Projects → New project**, вибери Board, додай до нього Issues цього репозиторію та налаштуй поле Status за таблицею вище. Issues залишаються джерелом вимог і обговорення; Project показує їхній стан.

## Коли задача готова до роботи

- Пояснено проблему або очікуваний результат.
- Межі зміни відомі: що входить у роботу і що лишається поза нею.
- Критерії приймання можна перевірити.
- Зрозуміло, хто відповідає за задачу та як перевірити результат.
- Для змін даних, SQLite або взаємодії з ПК описано вплив на наявні дані та сумісність.

## Коли робота завершена

- Критерії приймання виконані.
- Pull Request пов’язаний із Issue та пройшов перевірку.
- Для змін коду успішно виконана збірка `dotnet build LEOPARD.slnx -c Release`; релевантні ручні сценарії перевірені.
- Документацію оновлено, якщо змінилися поведінка, налаштування чи обмеження.
- Issue закрито після злиття.

У репозиторії наразі немає окремого автоматизованого test project. Для змін, які потребують тестування, в Issue треба вказати конкретний сценарій перевірки; наявний короткий ручний сценарій описаний у головній документації.

## Особливості LEOPARD, які треба враховувати

Застосунок — desktop-програма на C#, .NET 10, Avalonia UI та MVVM. Наразі він зберігає дані локально у SQLite; синхронізація між адміністративними ПК, серверний API, облікові записи та приймання платежів не реалізовані. У пропозиціях, які змінюють ці межі, окремо опиши архітектурний вплив, міграцію даних, безпеку та розгортання. Не вважай нарахування за сеанс фактом оплати.

## Публічність і дані

Репозиторій відкритий. Усі Issues, коментарі та Pull Requests можуть бути видимі публічно. Не додавай справжні дані клієнтів, номери телефонів, копії SQLite-бази, паролі, ключі агента, токени або логи з такими даними. Для прикладів використовуй вигадані значення чи очищені матеріали.
