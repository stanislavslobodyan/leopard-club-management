# Шаблон технічного завдання для LEOPARD

Скопіюй цей шаблон у GitHub Issue або заповни форму **Технічна задача**. Для невеликої зміни достатньо коротких відповідей. Для великої функції, зміни схеми SQLite чи мережевої взаємодії заповни кожен відповідний розділ до початку розробки.

## 1. Назва та пріоритет

- **Назва:** коротко описує результат.
- **Тип:** помилка / нова можливість / технічна робота.
- **Пріоритет:** P0 терміново / P1 високий / P2 звичайний / P3 низький.
- **Відповідальний:** GitHub assignee, якщо вже визначений.

## 2. Контекст і мета

Опиши, хто стикається з проблемою, у якому сценарії та чому потрібна зміна. Сформулюй результат для користувача або команди.

## 3. Обсяг

- **У межах задачі:** конкретні екрани, поведінка, дані чи компоненти.
- **Поза межами задачі:** суміжна робота, яка не повинна непомітно додатися до цієї задачі.
- **Залежності:** інші Issues, рішення чи доступи, без яких робота не почнеться.

## 4. Вимоги

Записуй функціональні вимоги окремими перевірними пунктами (FR-01, FR-02…). Якщо це важливо, додай нефункціональні вимоги щодо швидкодії, доступності, безпеки, надійності або сумісності.

Для змін інтерфейсу опиши основний сценарій, валідацію, порожній стан і помилки. Для змін у даних опиши поля, правила збереження, міграцію та збереження наявних записів.

## 5. Технічний підхід

Вкажи відомі компоненти, яких торкнеться зміна:

- Avalonia View/AXAML та стан екрана у ViewModel;
- сервіси й запити SQLite у ClubRepository;
- моделі даних і зміна схеми;
- конфігурація, публікація застосунку або документація.

Якщо спосіб реалізації ще треба дослідити, познач це явно. Не фіксуй передчасно деталі, які можна вирішити під час технічного аналізу.

## 6. Критерії приймання

Критерії мають описувати спостережуваний результат. Наприклад:

- [ ] Адміністратор може виконати потрібну дію з екрана …
- [ ] Некоректні або конфліктні дані відхиляються з зрозумілим повідомленням.
- [ ] Після перезапуску програми збережені дані лишаються доступними.
- [ ] Наявні записи та історія не втрачаються після оновлення схеми.

Залиш лише пункти, релевантні цій задачі.

## 7. Перевірка

Опиши команди збірки та конкретні кроки ручної перевірки. Для змін коду базова команда збірки — `dotnet build LEOPARD.slnx -c Release`. Якщо тест покриває сценарій автоматично, вкажи відповідний тест; автоматизованого test project наразі немає.

## 8. Ризики та супровід

- Ризики для користувачів, даних або сумісності.
- Рішення, які треба отримати від команди.
- Документація, інструкції чи кроки розгортання, що мають змінитися разом із кодом.

## Перевірка готовності вимог

Перед початком роботи інша людина має зрозуміти з Issue, яку проблему вирішує зміна, що вважається успіхом і як перевірити результат. Якщо цього не можна визначити, спочатку уточни технічне завдання.
